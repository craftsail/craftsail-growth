# Google 数据同步与分析改进计划

日期：2026-10-08 制定，2026-10-09 更新。状态：计划内本地实现与自动验证已完成，真实 Google/MySQL 验收待执行。分支：`plan/overseas-growth-optimization`。属于[出海优化计划](overseas-growth-plan.md)的第一阶段，细化 PR1，并将 PR7 的基础渠道分析提前。

当前体验的主要问题是：部分关键报表缺失，已有明细没进入分析接口，历史同步可能有缺口，页面缺少比较和下钻。第一阶段交付应让用户完成一次“发现变化 → 找到页面或渠道 → 查看证据 → 接受行动”的分析。

## 一 核对范围

已核对 Google 请求、事实表、同步游标、聚合服务、HTTP 接口和搜索页面源码。也通过只读连接检查了本地 `data/craftsail-growth.db`：有 1 个项目，GSC/GA4 总量表、明细表、同步状态和原始响应表均为 0 行。因此下列实现行为可由源码确认，用户当前使用实例的实际完整度仍需用该实例的同步状态和报表覆盖核对；没有发起真实 Google 同步或修改现有数据。

## 二 初始基线：为什么看起来数据少且不好分析

本节保留最初代码审计发现；当前实现以文末十八批实施记录为准。

| 问题 | 已确认的实现 | 对分析的影响 | 优先级 |
| --- | --- | --- | --- |
| 页面数据源不独立 | [board.go](../internal/service/webstats/board.go) 从 query-page 行生成页面榜单和衰退数据 | 看不到隐藏查询贡献的页面表现，页面变化可能失真 | P0 |
| 查询口径也需区分 | [keywords.go](../internal/service/webstats/keywords.go) 把 query-page 聚成 query，缺少独立 date-query 报表 | 多 URL 对同一查询有展示时，不等价于 GSC 按资源聚合的查询表现 | P0 |
| 日期固定 | [run.go](../internal/service/webstats/run.go) 的 `window()` 固定为截至 3 天前的 28 天；Snapshot 趋势只取最新 28 天 | 存了更长历史也无法自由查看，不能比较发布日期前后、近 90 天或完整周 | P0 |
| 截断后才筛选 | [board.go](../internal/service/webstats/board.go) 返回前 200 行；[keywords.tsx](../web/src/features/search/keywords.tsx) 仅在已返回行内搜索排序 | 低点击长尾词可能无法搜索到；CSV 也只导出已返回数据 | P0 |
| 维度采集了但读不到 | [slices.go](../internal/service/webstats/slices.go) 拉国家、设备、搜索类型和组合维度；[repo/webfact.go](../internal/repo/webfact.go) 的主分析读取只用 Web query-page | 无法判断是哪个市场、设备或搜索类型造成变化 | P0 |
| GA4 大量字段闲置 | [ga_facts.go](../internal/service/webstats/ga_facts.go) 已请求来源、媒介、campaign、落地页、国家、设备、互动、关键事件和收入 | [analyze.go](../internal/service/webstats/analyze.go) 只生成少量汇总；前端未呈现渠道和落地页分析表 | P0 |
| 请求字段没有保存 | GA4 请求 `userEngagementDuration`、`eventValue`，但解析与模型没有对应值 | 即使 API 成功，也无法从结构化事实分析互动时长和事件价值 | P0，先补用得上的时长 |
| 明细历史中断后可能跳过 | [backfill.go](../internal/service/webstats/backfill.go) 首次从旧日期往前拉；只要游标非空，后续仅取最近 10 天 | 初次同步中途停止后，不会沿历史断点补齐；长期停同步也会留空档 | P0 |
| 总量的停机缺口也未兜底 | [official.go](../internal/service/webstats/official.go) 非首次运行只刷新最近 3 天并向更早历史回填 | 上次完成到本次尾部之间可能缺天，不能只修明细游标 | P0 |
| 资源切换共用游标 | WebSyncState 唯一键是 project + source；Google property 不在 key 中 | 切换 property 后可能沿用旧资源回填进度；事实表隔离不等于进度隔离 | P0 |
| 更新只 upsert | [repo/webfact.go](../internal/repo/webfact.go) 没有按成功完成的切片范围替换旧行 | Google 修订后不再返回的旧行可能残留；重复拉取不保证与最新结果一致 | P0 |
| 同步部分失败不清楚 | `Run()` 把错误拼进 `IndexNote` 后可能返回 nil error；[jobs/wire.go](../internal/service/jobs/wire.go) 不输出该 note | job 可能显示 done，而部分明细未成功；来源卡主要表示总量导入状态 | P0 |
| 前端等待与后台脱节 | [webstats.tsx](../web/src/features/search/webstats.tsx) 最多轮询 240 次，之后退出 busy；提示没有完整的终态处理 | 后台继续运行时用户可能以为已结束，刷新页面也难以恢复进度 | P0 |
| 索引只是局部快照 | 先取最多 30 个目标，再跳过 7 天内检查过的项 | 不能解释整站发现、收录和新页成长，按原计划 PR4 处理 | P1 |

“GSC 查询词少”也有平台侧原因。API 明细有行数和聚合限制，维度越细不一定越完整；同步程序应准确声明覆盖，不承诺获得 Google 不提供的明细。[Google 数据获取说明](https://developers.google.com/webmaster-tools/v1/how-tos/all-your-data)

## 三 先围绕六个分析问题组织产品

| 用户要回答的问题 | 入口和操作 | 看到的证据 | 能做的决定 |
| --- | --- | --- | --- |
| 最近到底哪里变了 | 效果页选择 7/28/90 天或自定义日期，与前一等长区间比较 | 趋势、绝对变化、百分比、完整天数、贡献最大的页面 | 先查流量集中变化的页面 |
| 哪些词值得优化 | 查询列表按展示、点击变化、排名区间和品牌属性筛选 | 查询趋势、关联页面、国家和设备构成、样本量 | 修改目标页，或先等待更多证据 |
| 这一页为什么没效果 | 点击页面打开详情 | 页面独立搜索表现、可见查询、落地会话、互动和指定关键事件 | 区分搜索曝光问题与到站后的使用问题 |
| 海外哪个市场有效 | 国家和设备 tab 或筛选 | 独立总量切片、页面/查询明细及变化贡献 | 聚焦具体市场，排查移动端表现 |
| 哪个渠道带来有效访问 | 渠道与落地页 tab | source/medium、会话、互动、价值事件、同期变化 | 决定继续在哪个渠道投入 |
| 数据是不是没同步全 | 所有视图的覆盖摘要与同步详情 | 每报表范围、缺口、错误、最后成功时间和待补任务 | 重试具体范围，或先暂停下结论 |

例：过去 28 天 Google 点击减少 40 次，页面表显示 `/pricing` 减少 30 次。点入后筛选美国、移动端，查看该页面的搜索变化和 GA4 Google 自然搜索落地情况，再决定是检查搜索曝光还是页面交互。这里是预期操作示例，不是对真实站点的诊断结果。

## 四 报表数据契约

### GSC 使用不同粒度的事实

| 报表 | 所需粒度 | 当前状态 | 使用位置 |
| --- | --- | --- | --- |
| 全站趋势 | date × search type，不带 query/page | date-only 仅 Web 已有 | 效果页总量与对比 |
| 页面趋势和榜单 | date × page × search type | 缺失 | 页面列表、页面详情、页面衰退 |
| 查询趋势和榜单 | date × query × search type | 缺失，目前从 query-page 聚合 | 查询列表、品牌拆分、自有 CTR 参考 |
| 查询与页面对应 | date × query × page × search type | 已采集 | 双向下钻、URL 交替出现线索 |
| 国家和设备总量 | date × country；date × device；需要联动时 date × country × device | 前两者已有，联合总量缺失 | 国家和设备的来源正确的汇总 |
| 页面按地区设备 | date × page × country × device | 缺失 | 过滤后仍不依赖 query 的页面表现 |
| 查询按地区设备 | date × query × country × device | 缺失 | 过滤后的查询榜单，不能由 page 明细冒充同口径 |
| 查询页面详细诊断 | date × query × page × country × device | 已采集 | 具体页面和词的市场差异 |
| 搜索外观 | 支持的 appearance 类型与对应过滤查询 | 现有 date + appearance 请求需核验兼容性 | 后续专题诊断，不阻挡基础报表 |

这些粒度是查询契约，不代表全部组合每天全历史预拉。首轮保证 Web 总量、页面、查询、国家、设备及下钻必需切片，其他组合按已用筛选、有配额预算时回填；尚未具备的组合明确提示待同步，不使用别的粒度凑数。

总量随筛选变化时必须匹配对应粒度：国家 + 设备筛选不能把两个独立汇总表 join 出伪交叉数据；带页面筛选的总量明确是页面聚合。保留 Google 响应的聚合类型和请求版本。

GSC 高维明细优先按单日分页，记录请求日和返回量，避免多日大切片难以判断覆盖。搜索类型按项目启用，Web 优先；图片、视频等按实际需求拉取，Discover 等不支持的维度跳过并解释，不为所有类型盲跑同一套切片。Google 当前说明支持每日分页，且 Search Analytics 对每搜索类型每天有 50K 行数据上限；搜索外观需要专门的两步查询。[官方取数约束](https://developers.google.com/webmaster-tools/v1/how-tos/all-your-data)

### GA4 以渠道和落地页质量为第一交付

首轮展示已经可取得且有明确含义的会话、互动会话、关键事件次数，并保存互动时长。增加低维报表，避免所有信息都依赖一个包含 campaign、landing、country、device 的高维 session 报表。每个报表保留元数据和币种；GA4 收入只作为所选报表的分析值，不当财务收入或 MRR。

指定价值事件由项目配置，例如 `signup_completed` 或 `tool_succeeded`。总事件表只回答该事件发生多少次；“哪个落地页或渠道产生它”必须使用兼容的来源维度与事件过滤报表，不能把 date-event 表与 session 表按日期直接拼接。

新增或修改模板时检查指标与维度兼容性，保存模板版本；兼容性检查失败只影响该模板，不让所有 GA4 数据都不可用。[GA4 checkCompatibility](https://developers.google.com/analytics/devguides/reporting/data/v1/rest/v1beta/properties/checkCompatibility)

活跃用户数不能从按日、国家或落地页分组的值相加成整个窗口的去重用户；第一版渠道表优先用会话指标。互动率由匹配粒度的互动会话除会话计算；会话关键事件率由相应 GA4 报表取得，取不到显示不可用。跨分组汇总前验证指标是否可加，不能直接平均比例。

### GSC 与 GA4 的对应关系

页面详情并列展示 GSC 搜索效果与 GA4 落地效果，不宣称逐次点击或逐个用户串联。关联时使用完整 hostname + path，去掉 fragment 和明确的跟踪参数；保留会改变页面内容的参数及原始 URL，不把路径大小写、子域和尾斜杠一律合并。GA4 需要补 host 维度或获得明确的数据流域名映射，不能给所有路径强行加项目域名。

GSC 往往按 canonical 归属数据，GA4 反映实际落地路径；一对多映射显示依据和未匹配项。日期范围相同不代表时区相同，两个来源的日界线分别标注。Google 搜索点击的对照只取 GA4 的 `google / organic`，其他渠道另外呈现。

## 五 同步应该如何运行

### 分开追踪已完成范围与最新水位

新增按 `project + property + source + report + search type + request version` 隔离的同步状态，并记录已成功覆盖的日期区间或分区。不要只用一个 `last_end` 推断历史完整。

1. 首次同步优先最近 56 天，满足 28 天与前一窗口比较的基本需要，然后后台向历史扩展。GSC 在可取范围内回填；GA4 从用户选择的起点或合理默认范围开始，不再固定从 2020 年遍历。
2. 正常增量从上次连续成功边界追到新的可用日期；最近若干天另外重刷，以接收修订。中间断了一个月，恢复时补该月，不只刷新最近 3 天或 10 天。
3. 同步任务可按时间和请求预算暂停，未完成分区保留在队列；失败、取消、重启后从缺口继续。
4. 同一 property 的请求共享限流和重试预算。GA4 请求记录剩余 quota，减少不必要的高维和长区间查询。[GA4 配额机制](https://developers.google.com/analytics/devguides/reporting/data/v1/quotas)
5. 索引检查和报表历史回填分开调度；稀有搜索类型或坏模板不能挡住最新 Web 和 GA4 基础报告。

### 刷新成功范围时替换旧快照

取完某个报表某天的全部可返回分页并通过完整性检查后，在事务中替换该请求范围的旧事实并更新覆盖状态。收到合法空结果时允许移除该范围的旧行；请求失败、只收到部分分页或已知被截断时不能清空旧数据，也不能标为完整。即使程序取完分页，仍保留 GSC 平台本身的明细覆盖限制。

同时运行的历史回填与尾部刷新需要任务去重和写入版本保护，避免晚到的旧请求覆盖新结果。原始响应和同步日志保留请求范围与版本，用于解释变化；已有数据迁移时标为完整度未知，再渐进重刷。

### 返回用户能看懂的完成状态

同步详情展示每报表的可用起止日期、完整天数、缺口、最后成功时间、当前任务和错误分类。总体状态区分完成、部分完成、等待配额、失败、后台回填中；报表请求成功但数据为空与权限拒绝分别提示。

复用 jobs，不要求为 Google 重写全局调度器。补结构化结果而不是把错误混进 `IndexNote` 字符串；来源卡不要以 date-only 成功代表所有明细成功。前端刷新后能重新找到在跑的 job，轮询到期只表示界面停止等待，不显示同步完成。

## 六 分析界面与 API

继续使用现有“搜索流量”页，页内 tab 为效果、查询、页面、国家与设备、渠道与落地页；收录 tab 在原 PR4 交付。导航集中登记，不新增可折叠菜单。

### 共同操作

- 日期：7/28/90 天、自定义，展示实际可用范围；比较前一等长区间，历史不足明确标识。按日或周汇总，完整周不混入残缺周。
- 筛选：GSC 的搜索类型、国家、设备、页面、查询、品牌属性；GA4 使用来源、媒介、国家、设备、落地页和价值事件。筛选有作用域，查询筛选不假装能传给 GA4。
- 所有关键筛选写入 URL，切 tab 或下钻后保留能应用的条件，不支持的条件明确说明。
- 排序、搜索、分页在服务端作用于完整匹配集合。返回总匹配数或明确未知、下一页游标、是否截断；导出同一筛选下的全部可用匹配结果，不能只导出前 200 行。
- 零展示与“这一天未同步”使用不同图形或文字，不把缺失日补成 0。前期为零时显示新增及绝对变化，不显示无限增长率。

### 页面和查询详情

页面行打开详情面板，展示两期趋势、绝对变化、关联查询、地区设备、收录检查、已有行动与改动日期。查询行打开对应页面列表和稳定时间序列。先呈现事实，再给可接受为任务的建议。

页面榜单至少支持增长最多、损失最多、新出现、停止有展示、展示多但点击少几个视图。新出现或停止有展示依赖前后窗口都完整；历史缺失只显示未知。多页面对应一个词提供对照，不能直接输出“合并页面”。

### 建议的查询契约

扩展已有项目 API，新增明确的报表查询对象，而不是继续让 `SearchBoard(ctx, slug)` 固定日期。查询对象含 `from/to`、`compare`、`grain`、`search_type`、匹配本来源的 filters、`sort`、`limit/cursor`。DTO 至少返回：

| 字段 | 含义 |
| --- | --- |
| `scope` | source、property、报表版本、聚合粒度、时区、当前筛选 |
| `range` 与 `comparison_range` | 请求和实际生效的区间，明确是否完整 |
| `quality` | finalized-through、缺口、采样、阈值、截断、同步时间 |
| `totals`、`series`、`rows` | 同口径的总量、趋势和列表，缺失值为 null |
| `pagination` | 下一页游标及匹配数量的可用性 |
| `diagnostics` | 有具体证据定位和质量门槛的分析线索 |

复杂查询在 repo 按白名单字段聚合和过滤，继续遵守权限与 project/property 隔离。分页采用稳定的次级排序键，避免数值并列时重复或漏行。未经授权的只读用户不能触发补采集；GET 查看优先读本地，不因切筛选隐式发起无预算的 Google 请求。

## 七 交付顺序与验收

| 交付 | 对应原计划 | 内容 | 估算 |
| --- | --- | --- | --- |
| G1 | PR1a | 同步范围、property 游标、缺口续跑、修订替换、部分成功与进度 | 4–6 个工作日 |
| G2 | PR1b | 独立页面/查询与必要筛选切片、GA4 时长和质量元数据、按粒度读取 | 3–5 个工作日 |
| G3 | PR1c | 日期比较、全量筛选分页、页面与查询详情、国家设备分析、导出 | 4–6 个工作日 |
| G4 | PR7a | 基础渠道和落地页质量、指定事件分析、页面关联 | 3–5 个工作日 |

以上按 1 名熟悉仓库的开发者估算，共 14–22 个工作日，包含对应测试和三语检查。G1、G2 可逐项交付，G3 不等待多年历史全部完成；最近两期数据齐备即可使用。没有实际样本支持的维度不做强行凑数。

必要验收场景：

1. **中断续传**：历史第 2 个分区请求失败后重试，缺失范围补齐；停同步 30 天后恢复，总量和明细都无未解释的日期空档。
2. **资源隔离**：同一项目 A 切 B，B 从自己的覆盖范围开始；切回 A 可继续自己的历史。不同项目看不到彼此数据。
3. **修订与空值**：先返回两行，再成功返回一行，消失行不残留；分页中途失败保留上次成功快照并标旧；合法空报表不被标成请求失败。
4. **粒度正确**：页面点击 10、可见查询仅 3 时分别展示；一个查询对应多个页面时，查询原生汇总与页面明细各自保留，不能强制相等。
5. **数据可找到**：第 201 条低点击查询可以通过搜索找到；日期、筛选、分页和导出的结果范围一致；跨页并列排序稳定。
6. **比较可信**：只导入前期 7 天、当期 28 天时不判增长；属性时区跨日和夏令时边界不漏日；缺失日与真实零分开。
7. **GA4 口径正确**：互动时长成功入库；两事件/会话显示为次数指标；跨天重复用户不直接求和；指定事件与渠道无兼容报告时显示不可用。
8. **操作完整**：用户能在同一流程从总点击变化下钻到页面、查询、国家设备，再进入对应行动；所有 en/zh/pt 文案、空态和错误态同步完成。
9. **失败可见**：总量成功但明细 429 时显示部分完成及等待配额；刷新可恢复任务状态，前端轮询超时不伪装成功。

实现阶段采用 SQLite 夹具、Google HTTP mock 和现有前后端检查；影响日期、upsert、唯一键的迁移同时验证 MySQL 8。当前只补充分析与计划，未修改业务逻辑或运行真实数据回填。
