日期：2026-10-09。状态：PR1–PR8 的仓库实现及本地自动验证已完成，真实环境与产品验证待执行。工作分支：`plan/overseas-growth-optimization`。代码基线：`a7409f2`。

目标是让出海独立开发者和小团队每周回答三个问题：用户能不能从搜索和 AI 找到我，本周最值得改哪一件事，改完以后有什么证据说明值得继续。

### 产品定位假设

优先验证的人群：已经有公开网站、自己负责获客、能配置自托管工具的独立开发者和小团队。核心任务是每周定位一个可执行的搜索或 AI 获客问题，并追踪后续表现。英语市场作为首轮验证范围，继续完整支持现有中文、英文和葡萄牙文界面。

建议的一句话定位：**帮助出海小团队把搜索和 AI 可见性证据变成每周可执行、可复查的增长行动。**这是待用户访谈验证的定位，不是已证明的市场结论。

两个范围分别推进：

- 产品内：监测客户项目的搜索、AI 曝光、落地页和行动结果。
- 产品自身运营：用人工试用和本地行为记录验证 growth 的激活与留存。不能把客户网站的 GA4 会话当成 growth 的产品活跃。

首轮保留 React + Vite 看板、Go 单二进制、SQLite 默认和 MySQL 8 可选架构。书里对公开内容站静态 HTML 的建议用于客户站点检查和未来公开文档，不据此把登录后的看板迁移到 Astro。

## 三 实施前统一指标含义

### 搜索数据的边界

站点总量用 date-only 数据；页面效果用独立 date-page 数据；查询和 query-page 用于诊断。页面聚合与资源聚合并不等价，不能为了让数字相等而补齐或缩放。Search Analytics API 也不保证返回全部明细，要记录分页与覆盖情况。[官方接口说明](https://developers.google.com/webmaster-tools/v1/searchanalytics/query)

同一次比较必须使用相同 property、search type、过滤条件和完整窗口。沿用已有 finalization 信息；新报表不得只凭“有几行数据”判定窗口完整。成功取得的零值与尚未导入、截断、失败分别表示。比值分母为零时返回不可计算，不显示“增长 100%”。

查询可见点击与总点击之差只能提示覆盖差异，不能全部命名为“匿名查询量”。隐藏查询、截断、聚合范围与筛选差异都可能影响结果。非品牌查询占比必须注明基于可见查询，不能冒充全量份额。

### 新页面的时间与覆盖

《SEO 的监测》用首次展示近似“收录时长”，《新站的 SEO 监测》已将两者分开。实现采用后者的区分，并保留观察局限：

| 指标 | 产品定义 |
| --- | --- |
| 发布日期 | CMS、明确的 `datePublished` 或人工确认；保存来源，不能用数据库创建时间或 sitemap `lastmod` 替代 |
| 首次发现日期 | 本工具首次看到 URL 的时间；单独保存 |
| 首次观察到收录 | 首次成功检查到已收录的时间；不是 Google 实际收录时刻 |
| 观察收录耗时 | 首次观察到收录减发布日期；已知前一次未收录检查时可展示时间区间；旧页首次检查即已收录不计入新页耗时 |
| 首次展示日期 | date-page 事实中首次观察到正展示的日期；受历史回填范围限制 |
| 7 天观察收录率 | 有可靠发布日期且观察期已满 7 天的新页中，7 天内观察到收录的比例；监测中断者单列未知 |
| 索引状态 | 当前 URL 清单中的已检查收录、已检查未收录、未检查或过期，分别给数量 |
| 展示覆盖率 | 同一目标 URL 集合中，当前观察为已收录且过去 28 天有展示的 URL 数，除以当前观察为已收录 URL 数 |

检查覆盖不足时，不给全站精确索引率。展示覆盖率注明索引快照日期；索引状态与展示窗口不同步时，它只是运营观察。采样结果不能外推成全站精确数量。

URL Inspection 查询的是 Google 已持有的索引版本，不测试实时页面，也不提供提交收录能力。[官方接口说明](https://developers.google.com/webmaster-tools/v1/urlInspection.index/inspect)

### 转化和效果

- `关键事件次数 / 会话数` 是每会话关键事件次数，可大于 1；不能命名为用户转化率，也不能直接套二项比例置信区间。
- 会话转化率需要“至少触发一次指定关键事件的会话数 / 会话数”，由兼容的 GA4 报告获得；取不到就只展示次数，不从事件总数推算。
- CTR 始终用总点击除以总展示。Wilson 区间可作为小样本提示，但展示并不保证独立同分布，不把区间当成 SEO 因果证据。
- “修复已验证”和“业务效果改善”是两条结论。技术问题消失不能直接推出收入、点击或 AI 推荐增加。
- AI API 采样、人工网页采样、GA4 可识别的 AI 引荐会话分别呈现。提及率不是用户流量，引用不是点击，缺失 referrer 不是零 AI 贡献。

书中百分比告警线、500 次展示和 PMF 40% 等数值作为起始经验，不作为平台规则或自动过关证明。文中 2026 年的新功能和会议时长，不直接写成产品 SLA。Google 当前文档说明 AI 搜索展示不要求额外的 AI 文件或特殊 schema，相关访问计入 Web 搜索效果；保留 llms.txt 为辅助建议，不能承诺排名或推荐收益。[Google AI 搜索说明](https://developers.google.com/search/docs/appearance/ai-features)

## 四 P0 首次交付

### PR1 修正搜索页面数据和质量契约

**目标：**页面榜单、衰退分析和站点总量都使用适合各自问题的数据源，所有消费端能知道数据是否足够。

此项扩展为 PR1a、PR1b、PR1c：先修明细和总量的断点补齐、property 游标隔离、成功范围替换与部分失败反馈，再补独立 date-page、date-query 和必要的过滤粒度，最后交付自定义日期、同期比较、服务端搜索分页、全量导出和页面/查询双向下钻。已有国家、设备切片优先开放使用。仅修 date-page 后继续展示固定 28 天前 200 行，不算完成本阶段。

工作：

1. 给现有 GSC 切片增加 date-page，并按需增加不含 query 的国家和设备切片。独立分页、同步状态和回填，不能将旧 query-page 聚合伪装成迁移后的完整页面数据。
2. 将 SearchBoard 页面列表、页面衰退和相关报告切到页面事实；关键词分析继续使用 query-page。200 行 UI 展示上限不得限制全量诊断，提供分页或明确截断说明。
3. 在现有 WebImport 基础上补充按报表和窗口表达的质量信息：请求范围、实际覆盖天数、finalized-through、截断、最近成功同步、错误。质量状态随 API DTO 一起下发。
4. GA4 解析并保存 `subjectToThresholding`、`samplingMetadatas`、`dataLossFromOtherRow` 等元数据，原始响应继续保留；“受阈值约束”不等于证明已有数据被删。[GA4 元数据定义](https://developers.google.com/analytics/devguides/reporting/data/v1/rest/v1beta/ResponseMetaData)
5. 全部报表区分未知、真实零和部分数据；质量门槛供机会、告警、验收和报告共同使用。

主要位置：`webstats/{slices,gsc_facts,ga_facts,official,board}.go`、`repo/{webstats,webfact}.go`、`model/webstats.go`、`api/searchboard.go`、`web/src/api.ts`、搜索页面与报告。

验收：构造页面 10 次点击、可见查询只覆盖 3 次的夹具，页面显示 10、查询显示 3，站点总量保持独立；请求成功但没有结果与请求失败能区分；资源切换不串数据；中断或截断窗口不触发衰退告警；质量状态在 API、页面和报告一致。

### PR2 抑制小样本误判并增加新站观察模式

**目标：**小站先看到可检查的事实，不被低基数百分比和混合平均排名误导。

工作：

1. 新增项目搜索观察模式 `auto / new_site / established`，与 PMF 阶段、UI 语言、旧 `Market` 字段分开。自动模式显示判断依据，允许手动覆盖；升级条件使用持续多个完整窗口的数据，不因一天波动来回切换。
2. 新站优先显示完整周展示、点击绝对数、有展示页面数和数据覆盖，降低全站平均排名权重；PR4 完成后再加入索引生命周期。
3. 低 CTR 和流量下降先过 PR1 的质量门槛，再检查样本量、绝对变化与持续性。实现中将 500 次展示设为可配置的关键词候选行动门槛，并标为经验值；低 CTR 提醒暂不生成，等待 PR5 的本站参考。关键词候选保留，证据不足时只作为观察线索。
4. 不再凭全站平均排名下降就生成高优先级问题，改为具体页面和稳定查询集合的诊断线索。流量掉到零也必须区分真实归零和同步失败。
5. P0 停止把硬编码 CTR 表作为本网站应有表现；自有曲线在 PR5 实现。初期样本不足时展示事实和观察建议。

主要位置：`model/project.go`、`service/project`、`webstats/{alerts,searchops,board}.go`、搜索页、项目设置与三语词条。

验收：10 次点击降到 7 次不产生高优先级流量事故；新长尾进入导致平均排名变差而展示增加时不判定站点衰退；不完整窗口不比较；足量流量真实归零能进入诊断；相同输入的模式选择稳定且可解释。

### PR3 缩短首次价值时间

**目标：**输入网址后，用户知道发生了什么、卡在哪里，并能完成一次有证据的判断。

工作：

1. 先返回抓取与体检结果，再按已连接能力继续 Google 或 AI 任务。复用现有 jobs/pipeline；无需模型 key 的技术检查应可先完成，耗时来源不阻挡首批结果显示。
2. 消除首次 `startJob` 错误吞掉的问题，显示未启动原因和重试入口；重试必须复用项目，不重复创建。
3. 总览增加可恢复的设置进度：网址检查、品牌与问题确认、可选 Google 连接、可选 AI 采样、首个建议。只显示当前可完成的下一步。
4. 定义首次价值事件：用户打开含证据的诊断并明确接受或标为“有帮助”；采样次数、自动定时任务完成和登录不能代替用户获得价值。没有发现问题时允许确认诊断有帮助，不制造任务。
5. 增加演示、无 key、Google 未授权、站点不可达、部分成功等状态；保留无网站项目的人工资料和 AI 路径。

主要位置：`features/auth/onboard.tsx`、`features/settings/projects.tsx`、`features/overview/overview.tsx`、`service/{jobs,pipeline}`、行动接口。先用现有任务时间和显式交互记录测量，不接入默认外发遥测。

验收：无 AI key 仍能得到站点体检；Google 授权失败不会抹掉已有结果；任务启动失败可见且能恢复；刷新后进度仍在；无权限用户不能启动任务；完成英文、`?lang=zh`、`?lang=pt` 首次使用流程检查。

首轮体验目标：在固定演示夹具上 5 分钟内找到一条有证据的结论。真实外站耗时、可用率和用户 TTV 另行记录，不把夹具结果当生产 SLA。

## 五 P1 完成每周运营闭环

### PR4 新站 URL 清单与索引生命周期

**目标：**回答哪一批页面还没被发现、还没收录、已经收录但没有展示。

先建立独立于爬取上限的 URL 清单，支持 sitemap index、子 sitemap、去重和内容类型分组。保留 URL 所属 sitemap，处理重定向、canonical、删除和 noindex；不得简单累加父子 sitemap 的 submitted 数。发布日期缺失可人工补充，默认未知。

在现有 GscIndex 最新快照之外增加按 property 隔离的检查历史，保存 `googleCanonical`、`userCanonical`、检查状态和原始证据。已知状态来自结构化字段，Google 原始 `coverageState` 只作补充，不能靠中文字符串判断。

建立可恢复检查队列：新页、状态异常和最久未检查页优先；先筛到期目标再应用批量上限。官方当前 URL Inspection 配额为每资源每日 2,000、每分钟 600 次；本产品预算应更保守、可配置，并按同一个 Google property 共享，429 退避。[配额说明](https://developers.google.com/webmaster-tools/limits)

检查频率按页面状态设置，不默认全站每天重查。每天检查更多 URL 的收益需与配额、服务时长对照。展示已检查比例、下次检查和未完成原因。

主要位置：`service/webstats/{index,run}.go`、`service/crawl` 的 sitemap 解析、`repo/webstats.go`、`model/webstats.go`；新增 URL 清单、检查历史、队列模型；搜索页增加“收录”页内 tab。

验收：1,000 URL 夹具可分批完整轮转，首批不会长期占位；崩溃后续跑不重扣成功任务预算；切换 property 不读旧检查结果；无法确定发布日期不显示伪耗时；最近发布不足 7 天的页面不计入 7 天率分母；检查失败不等于掉索引；同一 URL 出现在多个 sitemap 时全站计数不重复。

### PR5 自有 CTR 参考和可解释的行动优先级

**目标：**给出本周最值得做的少数行动，说明证据、影响范围和投入。

用最近约 90 天完整数据构建非品牌查询的自有 CTR 参考，按 1–3、4–6、7–10、11–20 档聚合。优先匹配国家与设备，样本不足时退回更宽分组并注明；仍不足则不计算机会点击。仅用可见查询、保存数据范围和版本，必要时排除目标行，减少自身充当参考的偏差。

机会点击可用 `展示 × max(参考 CTR − 当前 CTR, 0)` 辅助排序，明确为情景估计，不是预测。多 URL 获得同一查询展示先标为“需诊断”：检查时间交替、意图和各页其他查询，不自动认定互相抢词，不自动建议合并。

行动排序保留确定性技术故障优先，再按项目阶段、证据强度、影响范围和工作量排序。同等级内提供可编辑 ICE 作为人工判断，不能把搜索机会点击与 AI 提及率拼成一个貌似精确的 ROI。默认推荐本周至多 3 个行动，其余保留在列表。

主要位置：`webstats/searchops.go`、`opportunity/{item,rank,service}.go`、`model/task.go`、`features/actions`。

验收：无站点参考时不退回“第 1 名应该 28%”的确定结论；品牌别名过滤沿用；相同输入排序稳定；每项能点到具体页面或查询证据；低质量窗口只展示待观察，不生成强结论。

### PR6 行动上线记录与独立效果观察

**目标：**从“任务完成”走到“修改后观察到了什么”，且不把相关变化写成因果。

扩展 Task，关联轻量观察记录：假设、主指标、护栏、目标 URL 或问题集合、负责人、投入、上线时间、固定基线、等待期、观察窗口、可选对照、结论与备注。复用已有 baseline 和 evidence，不再复制任务状态机。

技术修复可即时复查；搜索效果默认建议完整 28 天前后窗口，样本不足继续等待。AI 效果固定问题集合、引擎、模型、access 和采样策略；问题编辑、模型变化或窗口重叠时标为不可直接比较。基线和观察快照冻结，重跑可追溯版本。

结论区分：待观察、观察到改善、观察到下降、证据不足、不可比较。观察结果独立于 Task 的 open/doing/done/verified/regressed。补搜索效果检查，但不要把现有 manual 任务批量迁成自动通过。达到预先约定窗口再评估，避免每天重复检验直到“显著”；统计区间不代表因果证明。

主要位置：`model/task.go` 与新增观察记录、`repo/task.go`、`service/verify`、`api/opportunity` 相关入口、行动详情与报告。

验收：上线前样本不进入上线后窗口；少量新数据不能让任务变为效果改善；修改发生前的旧审计不能验证新修复；Google 断连保留待观察；多个同时改动的页面显示干扰说明；既有手工任务和 API/Web 分离行为保持兼容。

### PR7 渠道质量与阶段周报

**目标：**把“看到了”与“来了、做了什么”放在同一周复盘中，明确每个数的来源。

基础渠道和落地页分析作为 PR7a 提前到 P0；阶段周报、观察结论和报告语言作为 PR7b 留在 P1，避免用户等到整个行动系统改完才能分析 Google 数据。

复用 GA4 session facts，先提供渠道与落地页的会话、互动会话、关键事件次数和可用的会话关键事件率。区分所有 organic 与 `google / organic`；GSC 点击只能与后者作诊断性对照，时区不一致时说明，不能当精确漏斗。需要按指定价值事件分析时新增兼容的过滤报表，不能把现有 date-event 汇总直接 join 成渠道归因。

新增 `search/channels` 页内 tab，支持国家、设备、落地页类型筛选。AI 引荐复用现有识别逻辑；未知、direct、referral 保留原貌。UTM 规范与自报归因先写成接入指南，后续仅在有真实用户需求时做导入。

总览在 GEO 主体旁增加项目重点和“本周 3 件事”，链接到来源页面。每周报告包括：数据健康、阶段指标、最大的变化、执行的行动、到期观察结论、下周任务。新站以收录与展示为主；有稳定数据的站以机会、渠道质量为主；Google 未连接时仍可生成 GEO 报告。

报告增加 en/zh/pt 明确的语言选择和正确 HTML lang，新增文案按共享词条或生成资源实现，避免前后端各自硬编码。HTML 报告配色从 `web/src/styles.css` 的既有 token 生成或导出，不另设颜色体系。

验收：15 个关键事件、10 次会话显示为 1.5 次/会话，不能显示 150% 用户转化率；按日/国家汇总的 activeUsers 不能相加冒充窗口去重用户；缺失转化字段不显示零；页面和周报同源同窗口；三种语言的空态、错误、计数和报告均可读。

### PR8 目标市场与采样语言

增加明确的采样语言与目标地区配置，支持 en/zh/pt 问题模板和人工审核。界面语言、站点语言、问题语言、报告语言分别保存；切换界面语言不能悄悄改采样问题。复用问题标签与筛选能力，确认需要稳定分析维度后再增加字段。

先按所选引擎、问题数、重复数展示预计调用量，复用已有运行记录；若没有可靠单价就不显示虚假的金额估算。模板按访谈收集到的买家问法调整，不把文章观点直接当通用 prompt。地区配置表示目标人群，不承诺 API 模拟了当地消费者界面。

主要位置：`bootstrap/{run,filter}.go`、项目和问题配置、采样记录与筛选、三语帮助。旧 Market 已明确废弃市场拆分，不借它恢复旧模型。

验收：葡语项目生成葡语问题，UI 切换不改变问题；同一版本题库跨周期可比；不同语言的数据可分开查看；变更题库留记录；已有项目迁移后继续运行且不被静默改语言。

## 七 growth 自身的验证计划

以人工陪跑开始，阶段门槛是本项目的试验目标，不是行业 PMF 定律。即使客户站流量很小，也能验证用户是否看懂诊断、采取行动、愿意回来复盘。

| 时间 | 动作 | 记录和下一步 |
| --- | --- | --- |
| 第 1–2 周 | 访谈 10–15 位目标开发者，问上次排查搜索或 AI 获客时用了什么、花多久、最后做了什么 | 汇总原话、替代办法、反面证据；目标找到至少 5 位愿意带真实项目试用的人 |
| 第 2–4 周 | 陪 5–10 个真实项目完成首次诊断，每次观察配置、等待、理解与接受行动 | 记录 TTV 中位数和失败原因，优先修最常见阻塞；演示不计真实激活 |
| 第 4–8 周 | 每周与试用者复盘一次，跟踪接受、上线和复查记录 | 区分自动采集活跃与人的复盘；目标至少 3 个项目连续 4 周主动复盘，不达标先访谈原因 |
| 第 8–12 周 | 整理 PMF 证据卷宗，向持续使用者询问替代成本、缺失价值和付费意愿 | 行为、反面证据、样本量一起记录；有付款才算付款证据，不以星标或好评代替 |

自身北极星先定义为“每周完成一次有依据复盘的真实项目数”：用户主动查看诊断，并接受行动、确认有帮助或记录一项观察结论。项目为去重单位，自动任务不算。辅指标是首次价值到达率、TTV、从接受到上线的比例和成熟队列 W1/W4 复盘留存；小样本同时给分子分母。

保持 README 的无默认遥测承诺。第一轮可在陪跑表和实例本地记录结果；任何后续外部分析连接由实例管理员明确配置。样本未成熟的留存格留空，不能填 0。

长期渠道先验证书中真实案例与可复现教程，短期渠道先验证开发者社区中的人工演示。每次围绕一个具体问题展示证据，例如“查询点击和页面点击为什么不同”“为什么暂不建议改标题”。衡量带来的真实试用和复盘，不以曝光或 star 作为成功终点。这里只安排运营工作，不自动向社区或用户发消息。

### 数据与迁移约束

新增表和字段采用增量迁移，旧任务、旧报告和原始响应保留。新页面事实独立回填，旧数据质量标为未知；历史索引状态不可从最新快照捏造。默认关闭依赖新字段的强结论，回填完成后才启用。

查询必须包含 project/property 范围，检查历史与预算不能跨客户泄漏或相互覆盖。沿用 `cli → api → service → repo → model` 依赖方向，新增数据库读写放 repo；分析函数尽量保持输入输出明确。

SQLite 为必测后端。MySQL 8 验证复合索引长度、upsert、日期边界与迁移，避免直接照搬书中的 Postgres SQL。长 URL 使用既有哈希键模式，保存原文用于核对。记录检查历史和 Google 原始响应的存储增长，为保留周期和清理留接口。

新来源与新 UI 通过可回退配置逐步启用。回退时保留新表，只停新行为，不通过删除历史数据恢复旧版。同步失败继续展示最后一次成功数据及时间，不用旧数据伪装最新结论。
