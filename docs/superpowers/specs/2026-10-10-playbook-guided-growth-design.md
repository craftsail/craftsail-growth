# 按剧本指导：让 growth 照着 craftsail-book 带人做事

日期：2026-10-10。状态：第 0–4 期已实现（分支 `feat/playbook-help-center`，未提交）；书的新章待作者审定，MySQL 8 验收待跑。实现中与原设计不同的决定见第八节。

## 一、要解决的问题

craftsail-book 的主线是一套建模方法：

1. 你在哪个阶段（按结果分，不按时间分）；
2. 这个阶段的主力自变量是哪 1–2 个；
3. 每个自变量：怎么做、怎么量、哪些数不能信、什么时候算过关；
4. 每天 / 每周 / 每月的节奏和周报；
5. 用自己的数据校准，再写回书里。

growth 现在的主线是功能清单：可见性、声量、引用、扩展搜索、搜索 8 个标签页、观察记录……产品里没有任何地方回答“我在哪个阶段、这周该做什么、怎么算做完”。帮助中心 21 个主题按页面组织，大量是口径免责声明，讲怎么读数，不讲怎么做事。上一轮计划（`docs/overseas-growth-plan.md`、`docs/google-data-analysis-plan.md`）把精力放在数据底座，最上面“带人做事”的一层没有设计。

本设计先定义“带人做事”这一层，再按它审计已有功能。

## 二、边界

- **只做两个自变量：SEO 和 AI 推荐。** 社区、目录站、冷外联、账号等渠道不进产品，只在剧本里说明“这个阶段它们更重要”并链接到书。
- **书先于产品。** 剧本的每一步必须引用书里的一节。书里没有的方法，先补进书，再进产品。
- **底层数据不动。** Google 同步、索引历史、GA 明细、采样、体检、验收逻辑保留；改的是组织方式、引导层和界面。
- 不新增渠道、不新增数据源、不迁移前端框架。

目标用户：已经有公开网站、自己负责海外获客的独立开发者和小团队。

成功标准：新用户打开帮助中心的剧本，就能回答三个问题——我在哪个阶段；还有哪几步没做（点进去就是做这件事的页面）；离过关还差哪几条。学会以后，日常只看总览的数据，不再需要引导。

## 三、剧本结构

### 1. 先问产品阶段

剧本第一步问：产品过了 S0（约 100 个活跃用户、留存开始走平）没有？

没过时直接说明：按《流量公式与阶段权重》的权重表，S0 阶段 SEO 是 ★、AI 推荐是 ★★，都是滞后渠道。这个阶段在 growth 里只做“一次性设置 + 自动监测”，大部分时间给社区和手动拉人，并链接书里《PMF 验证与第一批用户》《怎么找社区》《目录站与 awesome 列表》《冷外联》。

这个回答保存在项目上（`product_stage`: `s0` / `s1` / `s2` / 未回答），可随时改。它只影响剧本的提示（S0 时在 SEO 和 AI 剧本顶部提醒“这个阶段主力不在这里”），不隐藏任何页面和步骤。

### 2. SEO 轨道

**SEO-1：Google 认不认这个站**（来源：《新站的 SEO 监测》）

| 节奏 | 做什么 | 页面 | 书 |
|---|---|---|---|
| 一次 | 体检的访问、发现、理解三层通过；连接 GSC / GA4 | 站点体检、Google | 《SEO 落地》十五；《SEO 的监测》二 |
| 每天（自动） | URL Inspection 轮查 sitemap 全部 URL；只在掉索引、5xx、索引率一天跌 5 个点以上时提醒 | 收录 | 《新站》三.4、七 |
| 每周 30 分钟 | 各 sitemap 索引率、新页收录时长、7 天收录率；周展示和有展示的网页数；本周首次出现展示的页面及其查询词；GA4 自然搜索会话和关键事件的绝对数 | 收录、概况、到站 | 《新站》七 |
| 每月 | 28 天零展示的已收录页：改、合并或 noindex；回看一个月前改过标题的页面 | 页面 | 《新站》七 |
| 这阶段别看 | 平均排名、CTR、周环比百分比、GA4 的比率。在这些数出现的位置写一句为什么，而不是到处加免责声明 | — | 《新站》二 |

过关条件：《新站》八的 8 个信号，在帮助中心的剧本里按当前项目逐条显示 ✓ / ✗ / 无数据。能从已有数据算出的信号自动判定，其余显示“需人工确认”：

| 信号 | 判定 |
|---|---|
| 新页 1–3 天内收录并开始有展示 | 自动：近 28 天新页的收录时长中位数 ≤ 3 天且有展示 |
| 各 sitemap 索引率稳定在高位 | 人工（在 Search Console 站点地图报告里看；本工具不保存各 sitemap 的索引率历史） |
| 已发现-尚未编入索引持续减少 | 人工（需 GSC 索引报告，API 不提供） |
| 每天抓取请求明显高于刚上线时 | 人工（抓取统计无 API） |
| 有展示的网页数占已收录的大多数 | 自动：展示覆盖率 ≥ 50% |
| 总点击与查询表点击之和的差距在缩小 | 自动：可见查询点击占比连续 4 周上升或 ≥ 50% |
| GSC 出现品牌词过滤 | 人工 |
| GA4 不再频繁出现阈值提示 | 自动：近 4 周 GA 报表的 `Thresholded` 标记（`internal/model/googlequality.go`）都为假 |

阈值是先验，写成常量并在帮助中心公开；以后用真实项目校准，再写回书。

**SEO-2：起量和守住**（来源：《SEO 的监测》）

每周：拆品牌词和非品牌词、自己的 CTR 曲线和 CTR 差距、机会点击（排名 8–20 的词）、下滑页面、周环比告警线。周报换成《SEO 的监测》八的模板。

阶段判定：8 个信号（自动判定或人工确认）满足至少 6 个，或搜索数据已把资源判为 `established`，就算过了 SEO-1。`internal/service/webstats/search_stage.go` 的晋级规则不改（见第八节）。

### 3. AI 轨道（书里先补一章）

书里没有 AI 推荐监测的章节。实施的第一步是在 craftsail-book 写《AI 推荐的监测》，内容覆盖下面三个阶段的依据、指标、误差和过关条件，由作者审定后再进产品。下表是草案：

| 阶段 | 问题 | 做什么 | 过关 |
|---|---|---|---|
| AI-1 抓得到 | AI 爬虫能不能拿到内容 | robots 放行 AI bot、llms.txt、无 JS 也有正文 | 体检的访问、发现两层 pass |
| AI-2 认得你 | AI 知不知道你 | 填品牌事实；看品牌问题上的认知度 | 认知度 n ≥ 30 且 Wilson 下界 ≥ 50% |
| AI-3 推荐你 | AI 推不推荐你，依据是什么 | 按买家原话写问题（《工具产品出海运营》三）；看引用缺口，找到被引用的目录、社区、测评，去上面出现（《目录站》六） | 不设终点，每周看可见性和声量趋势 |

### 4. 共用的每周循环

来源：《工具产品出海运营》十一（实验池、实验卡），《工具产品看数据》九（实验）。

- 行动清单 = 实验池。
- 接受一条 = 填一张实验卡：假设、指标、观察窗口。复用现有观察记录（`internal/model/observation.go`）。
- 每周：看本周数 → 从池里挑 1 个 → 上线记录 → 复查窗口已到的。
- 报告 = 书里的周报模板，按 SEO 阶段出新站版或常规版。

## 四、产品里怎么呈现

### 1. 一份步骤定义，两处使用

剧本步骤写成数据（`web/src/features/playbook/catalog.ts`），每步包含：

- `id`，所属轨道和阶段，节奏（once / daily / weekly / monthly）；
- 回答的问题、做什么、怎么算做完（i18n 键，en / zh / pt 同时加）；
- 跳转的页面（nav 里的路径，页面名用 `n("nav.*")`）；
- 引用的书章节（标题 + GitHub 链接）；
- 可选的完成检查 `check`：后端返回的检查 id。

帮助中心渲染完整剧本，并按当前项目显示每一步和每个过关信号的状态。引导是低频操作，学会了就不再需要，所以**不放在总览**：总览只放日常要看的数据，最多在页头放一个“查看剧本 →”的小链接，链到当前阶段的剧本。

### 2. 后端：一个只读的剧本状态接口

新增 `internal/service/playbook`，依赖方向 `api → service → repo → model`：

- `GET /api/projects/:slug/playbook` 返回：`product_stage`、`seo_stage`、`ai_stage`、每个过关信号的状态（`met` / `unmet` / `manual` / `no_data`，附数值）、每个完成检查的状态（`done` / `todo` / `no_data`，附最后时间）。
- 只读、纯计算，数据全部来自已有表；不新增后台任务。
- 新增字段：项目上的 `product_stage`；人工确认的过关信号存一张小表（项目、信号 id、确认时间、确认人）。迁移在 SQLite 和 MySQL 8 都要跑。

完成检查第一批（都能从已有数据判定）：

| 检查 id | 判定 |
|---|---|
| `google_connected` | 项目选了 GSC 资源 |
| `audit_access_pass` / `audit_discover_pass` / `audit_understand_pass` | 最近一次体检该层 pass |
| `index_checked_7d` | 7 天内有成功的 URL Inspection |
| `brand_facts_filled` | 品牌别名、目标用户、一句话定义（`Brand.Definition`）已填 |
| `questions_confirmed` | 题库当前版本已确认 |
| `sampled_7d` | 7 天内有成功采样 |
| `report_this_week` | 本周生成过报告 |
| `experiment_open` | 有一条已接受、未结束的行动 |
| `experiment_due` | 有观察窗口已到、未评估的记录（为真时是待办） |

剧本里检查未通过的步骤标 ✗，就是待办；不另做一份“本周清单”。

### 3. 页面审计

| 现在 | 处理 |
|---|---|
| 总览 | 内容不变，只加一个指向当前阶段剧本的小链接 |
| 可见性、声量、引用、回答 | 保留 |
| 扩展搜索 | 并入“引用”下的标签页 |
| 搜索 8 个标签 | 收成 5 个：概况、收录、查询词、页面、到站 |
| ↳ 国家、设备 | 变成概况 / 查询词 / 页面里的“按维度切开”选择器 |
| ↳ 渠道、落地页 | 合并为“到站”（GA4） |
| CTR 参考、页面映射 | 收进对应行的详情面板 |
| 行动清单 + 观察 | 保留，观察改称实验卡 |
| 站点体检 3 个标签 | 保留 |
| 报告 | 保留，内容改成按阶段的周报模板 |

在 SEO-1 阶段，查询词页顶部写一句“这阶段查询表只作线索”，不隐藏标签。所有旧地址在 `web/src/app/nav.ts` 的 `LEGACY_REDIRECTS` 里加跳转。

### 4. 帮助中心

21 个主题改成：

1. **从这里开始**：你的产品在哪个阶段；一次性设置。
2. **SEO 剧本**：新站阶段、起量阶段。
3. **AI 剧本**：抓得到、认得你、推荐你。
4. **每周 30 分钟**：节奏、实验卡、周报。
5. **按症状排查**：没收录、流量掉了、AI 不提我、Google 没数据……（来源《工具产品看数据》八“数字掉了怎么查”）。
6. **参考**：术语、公式（保留现有 `FX`）、连接与管理（模型、Google、计划、权限、更新）。

每一步统一写法：为什么（一句话 + 书的链接）→ 做什么（点进页面）→ 怎么知道做完了。口径说明只放在它影响的那一步，写成“这阶段别看这个数，因为……”。页面上的“?”提示（`web/src/app/tips.ts`）和 `helpTopicFor` 改为指向对应剧本步骤。

## 五、实施顺序

每一期单独可用，按顺序做：

0. **书**：在 craftsail-book 写《AI 推荐的监测》草稿，作者审定。
1. **帮助中心**：步骤目录 + 剧本式帮助中心（三语）。不依赖后端改动，完成检查先全部显示为未检查。这一期结束，帮助中心本身就能带人做事。
2. **剧本状态接口 + 帮助中心显示状态**：`playbook` 服务、`product_stage`、人工确认表、过关信号、完成检查；帮助中心剧本标出当前阶段、每步 ✓/✗、过关进度，可在剧本里选产品阶段、人工确认信号；总览加一个小链接；`search_stage` 晋级条件改为书的信号。
3. **页面收敛**：搜索 8→5、扩展搜索并入引用、详情面板、旧地址跳转、tips 重指向。
4. **周报**：报告按 SEO 阶段换成书里的两个模板。

## 六、验证

- 后端：`playbook` 服务的表驱动测试，覆盖每个信号和检查的 met / unmet / no_data；迁移和查询在 SQLite 上测（参照 `internal/invoker/sqlite_test.go`），`make test-mysql` 跑 MySQL 8。
- 前端：`tsc` 和 `vite build` 通过；`npm run check:cjk` 通过；目录里每个步骤的 i18n 键在 en / zh / pt 三个文件都存在、页面路径都在 `NAV` 里（加一个构建时检查脚本）。
- 浏览器：演示项目分别在 `?lang=zh`、`?lang=pt`、英文下走一遍：新站场景的帮助中心标出当前在 SEO-1、各步骤 ✓/✗ 正确，历史站点场景标出 SEO-2；总览只多一个链接；每个旧地址能跳到新页面。
- 产品：找 2–3 个真实新站项目试用一周，看用户能否不读帮助就说出“这周做什么”。结果写回书里对应章节。

## 七、不做

- 不做社区、目录站、冷外联、账号等渠道的记录或监测。
- 不做跨渠道的权重估计和建模。
- 不新增自动推送（邮件、Slack）。
- 不改 Google 同步和采样的数据口径。

## 八、实现中的决定（与上文不同之处）

| 原设计 | 实际 | 原因 |
|---|---|---|
| `search_stage` 晋级条件改成书的信号 | 不改；剧本自己判定 SEO 阶段（≥6/8 信号，或已是 `established`） | `search_stage` 决定统计告警何时启用，按样本量把关；绑到剧本会放松这层保护 |
| “各 sitemap 索引率稳定”自动判定 | 人工确认 | 没有保存各 sitemap 的索引率历史 |
| 引擎步骤“连接测试通过” | “至少一次采样成功” | 密钥测试结果不保存 |
| 完成检查 id（`audit_*_pass`、`brand_facts_filled`、`sampled_7d`、`experiment_due`） | `audit_layers_ok`、`audit_access_ok`、`sitemap_ok`、`llms_published`、`brand_facts`、`recognition_n`（近 30 天）、`experiments_reviewed`、`competitors_3`、`first_check`、`engines_answered` 等 15 个，定义在 `internal/service/playbook/judge.go`，与 `web/src/features/playbook/catalog.ts` 的 `CHECKS` 对应 | 按每一步“做完的标志”的文字逐条对齐 |
| 展示覆盖率用“28 天有展示的网页 ÷ 已收录” | “已收录且出现过展示的 URL ÷ 已收录 URL”，分子分母同一来源 | 原口径分子分母来自不同报表 |
| 周报“本周上线” | 近 7 天滚动窗口；周报表列头写明每周日期 | Search Console 有 2–3 天延迟，表格的“本周”是已完整的上一个自然周 |
| 搜索页 8→5 | 已做；国家/设备是“表现”页底部的“按维度切开”，渠道+落地页合成“到站” | — |
| CTR 参考、页面映射收进详情 | 原本就是详情面板，未改 | — |
| SEO-1 在出现 CTR/排名的位置说明 | 关键词、页面两页在新站阶段显示一句提示并链到剧本；表现页在新站阶段本来就隐藏平均排名图 | — |
| 观察改称实验卡 | 只改界面标题；数据和口径不变 | — |

阈值写在 `catalog.ts` 的 `THRESHOLDS` 和 `judge.go` 的常量里，`TestThresholdsMatchCatalog` 保证两处一致。
